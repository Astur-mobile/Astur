وتبقى الواجهة العامة بأسلوب Playwright:

```ts
await device.getByRole('button', { name: 'Sign in' }).tap();
await expect(device.getByText('Welcome')).toBeVisible();
```

وتتولّى بيئة التشغيل تحت تلك الواجهة اختيار الجهاز، ودورة حياة التطبيق، والبحث عن المحدِّدات الأصلية، وفحوص قابلية التنفيذ، والإيماءات، ولقطات الشاشة، والفيديو، والتتبّعات، ودعم الـ inspector وتوليد الكود.

ويحتفظ المصدر `docs/architecture.md` بمخططات Mermaid لقرّاء المستودع. أما وثائق Astro العامة فتستخدم نسخة MDX/CSS من الرسم نفسه، لأن Starlight لا يرسم كتل Mermaid تلقائيًا دون إضافة تكامل خاص بها.

## لماذا هذا سريع

تضيف الحزم التقليدية بأسلوب Appium خادم WebDriver بين الاختبار وإطار الأتمتة الأصلي. ويتفادى Astur طبقة ترجمة البروتوكول الإضافية هذه.

فللإجراءات الشائعة يرسل Astur النيّة مرة واحدة. ويحلّها وكيل المنصة وينفّذها محليًا، فلا يضطر المضيف إلى سحب أشجار واجهة كبيرة مرارًا لمجرد إعادة محاولة محدِّد.

## دورة الحياة مقابل التفاعل

ما زال Astur يستخدم أدوات المنصة حيث تكون هي الأداة الصحيحة:

- دورة حياة Android: يثبّت `adb` التطبيقات، ويشغّل الحِزم، ويلتقط لقطات الشاشة، ويسجّل الفيديو، ويجمع السجلات.
- دورة حياة iOS: يدير `simctl` و `devicectl` و `xcodebuild` المحاكيات وتثبيت التطبيق وتشغيله ولقطات الشاشة ومشغّل XCUITest.
- تفاعل العناصر: ينفّذ وكيلا Android و iOS الأصليان البحث والانتظار والنقر والتعبئة والسحب والتمرير وأوامر لوحة المفاتيح.
- ‏Flutter (‏Android): عند اكتشاف حزمة APK من نوع Flutter، يقرأ Astur شجرة الودجات الحيّة عبر **خدمة Dart VM** بدل UIAutomator، بينما يتولّى ADB دورة الحياة والإيماءات. راجع [Flutter و React Native](../frameworks/).

## الـ Inspector وتوليد الكود

يستخدم الـ Inspector في Astur بيئة التشغيل ونموذج المحدِّدات نفسيهما اللذين تستخدمهما الاختبارات.

ولا يخترع الـ inspector نظام محدِّدات ثانيًا. فحين يقترح محدِّدًا، أو يسجّل نقرة، أو يصدّر كودًا، يستخدم عقود المحدِّدات المحايدة تجاه المنصة نفسها التي تُنفَّذ أثناء تشغيل الاختبارات.

## قواعد الموثوقية

- فضّل المحدِّدات الدلالية على الإحداثيات.
- أبقِ الاستطلاع الأصلي داخل وكيل المنصة.
- استخدم لقطات الشاشة ولقطات الواجهة للتشخيص، لا كمسار تحكم افتراضي.
- أبقِ وكيل منصة واحدًا حيًّا لكل عامل Playwright متى أمكن.
- احجز جهازًا فعليًا واحدًا لكل عامل Playwright؛ فالتوازي الحقيقي يتطلب أجهزة متعددة.
- وحين تستخدم الإعدادات محدِّد جهاز فضفاضًا، دع Astur يختار جهازًا مطابقًا متاحًا من المجمّع المحلي بدل توجيه كل العمّال إلى الجهاز الأول نفسه.
- ولا تعد تشغيل التطبيق أو تصفيره بين ملفات الاختبار إلا حين يتطلب العزل ذلك.
- وأبقِ متطلبات XCTest في iOS صريحة بدل إخفائها خلف WebDriver.

## شكل الحِزم

يثبّت معظم المستخدمين:

```bash
npm install -D @astur-mobile/test astur-mobile
```

تمنحك `@astur-mobile/test` تجهيزة Playwright والتأكيدات. وتمنحك `astur-mobile` واجهة الأوامر، بما فيها `doctor` و `devices` و `init` و `test` و `codegen`. أما الحِزم الداخلية مثل `@astur-mobile/core` و `@astur-mobile/android` و `@astur-mobile/ios` فتبقى منشورة كحِزم npm عادية كي يظل المشروع معياريًا، لكن المستخدمين النهائيين لا يحتاجون ربطها يدويًا.
