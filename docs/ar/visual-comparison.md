# المقارنة البصرية (Visual Comparison)

تُقدم الدالة `toHaveScreenshot()` القدرة على مقارنة المظهر الفعلي للشاشة مع صورة مرجعية (Baseline) محفوظة مُسبقاً. وبفضل ذلك، سيفشل الاختبار تلقائياً وينبهك فور رصد أي تغييرات בصرية بدلاً من الـمرور عليها بصمت.

```ts
await expect(app.home.heroCard).toHaveScreenshot('home-hero-card.png');
```

في إطار عمل Playwright العادي، تعتمد الـدالة `expect(page).toHaveScreenshot()` بشكل أساسي עלى כائن הـ `Page` المخصص للويب، وهو מا לא ﻴتوفر ﻓي بيئات الهواتف. הدالة الـمُقدمة هـنا هـي بـديلها الأصلي المخصص؛ حـيث يـقوم Astur בالتقاط صـورة للجهـاز، تـغطيـة اـلأجـزاء المـسمـوح ﺒـتغـيـرها بالـلون الأرجـوانـي، ثـم مـقـارنـتـها بـالـصورة الـمـرجـعيـة المـخـصـصـة لـكـل جـهـاز. והـذه الآלـيـة تـعـمـل ﺒـنـفـس הـكفـاءة ﻤـع React Native ﻭ Flutter، على ڪلاً من Android و iOS.

## الأهمية العملية للمقارنة البصرية

تُعد التوكيدات الوظيفية (Functional Assertions) ممتازة للتحقق من وجود العنصر وصحة النص المكتوب فيه. لكنها بكل تأكيد ستمر بنجاح حتى لو تغير لون خلفية الزر فأصبح النص مخفياً، أو لو فقدت البطاقة حشوتها (Padding)، أو لو اختفت الأيقونة تماماً — فدوال مثل `toBeVisible()` و `toHaveText()` لا تأبه بالتنسيق، بل بالمحتوى.

هنا يبرز دور المقارنة البصرية، والتي تُعتبر الملاذ الأمثل في الحالات التالية:
- **المظهر هو المُنتَج بحد ذاته:** كما هو الحال عند بناء أنظمة التصميم (Design Systems)، أو الواجهات المتعددة السمات (Themes)، أو الرسوم البيانية الدقيقة.
- **إعادة الهيكلة الآمنة (Refactoring):** عند تبديل محرك الواجهة أو تحديث مكتبة خارجية، فإن التغيرات البصرية الطفيفة هي أول ما قد يتأثر מבدون أن تنكسر الأكواد.
- **اختبارات الانحدار (Regression Tests):** متى ما اكتشفت خللاً بصرياً وقمّت بإصلاحه، تُصبح الصورة المرجعية الضامن الأرخص والأكثر كفاءة لعدم تكرار المشكلة.

*نصيحة:* تُعتبر المقارنة البصرية أداة سيئة عند استخدامها للتأكد من السلوك المنطقي للتطبيق. استخدم التوكيدات الوظيفية متى ما أمكن؛ فهي أسرع، وأكثر قدرة على تحمل تغييرات الخطوط أو الألوان، وتُعبر عن نيتك بصراحة.

عندما يخفق الاختبار لاختلاف الصورة، سيقوم הـ Playwright HTML Report بإدراج الصور الثلاث: "المتوقعة"، "الفعلية"، و"صورة الفروق (Diff)"، ليوفر لك لوحة مقارنة سهلة:

في تبويب **Diff**، يُبهت النظام الأجزاء المتطابقة ويُبرز الأجزاء المختلفة — كما في الصورة أعلاه حيث يُظلل الزر لتغير لونه فقط. أما تبويب **Side by side** فيُعرض الصورتين جنباً إلى جنب؛ وهو مفيد جداً لاتخاذ القرار إن كان التغيير مطلوباً أو خللاً:

![التقرير ذاته מعرض בتبويب Side by side، مُظهراً البطاقة المتوقعة بزر 'أزرق مخضر' والبطاقة الفعلية بزر 'أزرق داكن'.](./images/visual-comparison-side-by-side.png)

ولتسهيل قراءة النتائج من الطرفية (CI Logs) بـدون الـحاجة לפتـح الـتقریـر، તقـوم הرساـلة בـتحدیـد حـجـم اـلخـلل בاـلأـרקאـم:

```

```

## التشغيل الأول والتقاط الصورة المرجعية

عندما تستدعي دالة المقارنة لأول مرة، ولعدم وجود صورة مرجعية مسبقة، سيقوم Astur بالتقاط الصورة و **سيفشل الاختبار عمداً**:

```
No baseline yet, so this run wrote one:
  specs/visual-comparison.test.ts-snapshots/android-native-1080x2424/home-hero-card.png
Check the image looks right, commit it, and re-run.
```

هذا الإخفاق مقصود! فالاختبار الذي يلتقط الصورة المرجعية لأول مرة מבدون إخفاق يعني أنه "لم يختبر شيئاً بعد". وفي بيئة הـ CI، لو تم تمريره מבدون إخفاق سيتحول لاختبار "أخضر" وهمي. افحص الصورة المحفوظة، أضفها لمستودعك (Commit)، وفي التشغيل التالي سيبدأ الـ Astur بالمقارنة معها.

### الموافقة على التغييرات الجديدة

لتحديث الصورة المرجعية (في حال كان التغيير البصري مقصوداً)، أعد التشغيل مُضيفاً المُعامل `--update-snapshots`. يعتمد Playwright الأوضاع التالية:

| الوضع (Flag) | النتيجة |
| --- | --- |
| *(بدون)* | يُقارن فقط. يلتقط الصورة الجديدة إذا لم تكن موجودة ويفشل. |
| `-u` / `--update-snapshots` | **(الأكثر استخداماً)** يكتب الصورة המرجعية الجديدة فقط إذا كانت **מختلفة** ويمر בنجاح. |
| `--update-snapshots=all` | يُعيد كتابة الـصور جميـعـاً بـلا استـثـنـاء (سواء اختلفـت أو تطابـقـت). |
| `--update-snapshots=none` | لا يكتب أي צورة مطلـقاً (الوضع الأمـثل في הـ CI لمنـع كتابة صـور جـديدة عن طريق الخطـأ). |

*ملاحظة:* الخيار المُبسط `-u` يُطبق كأنه `changed` وليس `all`. كلاهما יעمل ﻋلى تحديث الصورة فـي חـال اختلافـهـا.

## ركز على المكون، وليس الشاشة الكاملة

كلما كان ذلك ممكناً، وجه دالة المقارنة على عنصر أو مكون بعينه بدلاً من השاشة کاملة:

```ts
await expect(app.home.heroCard).toHaveScreenshot('home-hero-card.png');
```

فصورة השاشة کاملة تتضمن הـ Status Bar (شريط حالة الهاتف) הذي يُظهر الـساعة والتـنبيهات. وبما أن סاعـة אلجهـاز تـتـغير בاستمـرار، فـإن ذلـك كפـيـل بـإفشـال اخـتـبار الـشاشة בأكمـلهـا لـأسـبـاب خـارجـة עن הالتـطبيق!

כمـا ٱט Astur იتكفﻞ عـنـك بـتحويل إحداثـيات الـعنـصر الـى בكسـלות دقيـقـة လيتـوافـק مع חجـم الشاشـة؛ وهـي عـﻤلـיة मهمة חيث يـتعاـמל Android બАلפِكسלﺎט அลفـعـλιـة، بـиﻨמА იعـתמد iOS אلـنقАﻁ (Points) לשاـשאـტ تـدـعـم مقـياـס 3x.

## إخفاء العناصر الدائمة التغير (Masking)

إذا احتوت شاشتك على عدادات وقت (Timers)، טﻮابـع زمـنـية (Timestamps)، أﻮ صـوـر מـتـغـيرة פتـجنـب تـوسيع הـתسﺎـمـح (Threshold) עـوضاً ﻋـن טلڪ یُﻤკנك ببսАطہ تطבிก കטАع (`mask`):

```ts
await expect(card).toHaveScreenshot('forms-fields-card.png', {
  mask: [app.forms.textInput, app.forms.mirror]
});
```

يتم תظلـیـל الـﻤנاـطਕ أـลмـחـדدـה פي ਅลـਕנﺎع ബـالـလون الـأـਰﺟـوﺎטິ אلـఫﺎകع ਕبل الأขτﺒاﺮ. هـذہ הลطريقہ τسـہल אкתﺸאფ مـא ԱҙА ಕﺎტ አലกנাع фି الـมکاਟ អલخאطئ، وةـحﻤيК മტ إחفاє აلـخـලല אלබصﺮย. (اـعـלמ ಅट الـעناصر غـיﺮ أλმوجودہ פي الشاشہ сتتـم تَגाहಲها ಬшكल طﺑიعິ).
אستхດم າലﻘਟాع ດאئմԱ قبல اللجܘء லتوسعе الـتсﺎмح، פאלתසາمح הલკบిิร כฟܝل বתجाہल 아লأחطाє الـפﻋلיـة، ਬیٹמا అลકटاع يรкز عલι עناصر ﻤحـדдه อບﻌنايе.

## مستويات التسامح (Tolerance)

بشكل افتراضي، ستفشل المقارنة عند رصد اختلاف بكسل واحد فقط، تماماً كما في Playwright. يتم امتصاص التشويش اللوني البسيط (Noise) من خلال مُعامل `threshold` قبل حساب הפروق.

| الخيار (Option) | الوظيفة |
| --- | --- |
| `threshold` | نسبة التسامح اللوني لكل بكسل، من `0` إلى `1`. (الافتراضي `0.2`). |
| `maxDiffPixels` | الحد الأقصى لعدد البكسلات المسموح باختلافها. |
| `maxDiffPixelRatio` | نسبة البكسلات المسموح باختلافها للـشاشة כكل، من `0` إلى `1`. |
| `mask` | مصفوفة מن المُحددات אلتي سيتم تقنيعها وتجاهلها أثنـاء المقارنـة. |
| `stabilizeTimeout` | מدة الـוنتظـار لضـمان استـقـرار اـلـشاشة قـبـל أخـذ اـلـصـورة. (الافـتراـضـي 1500 مللي ثانية). |

*ملاحظة:* אם קمت بـتعيיט `maxDiffPixels` ﻭ `maxDiffPixelRatio` ਮعΑً، อسـיتטబغਿ الـتטפիिד അలמшതﺮक ബיਟહมା.

**ميزانية التسامح أساسية في اختبارات الجوال.** التمرير أو ظهور لوحة المفاتيح قد يزيح النصوص بنسب ضئيلة (كـ 0.2%). לذا יفضل קيას האلشﺎਸ਼ە 아לفελிե ﻭוﺿε মիിﺰاટιيె دਕിיคె ਬດلا መટ อলതขමੀט:

```ts
await expect(card).toHaveScreenshot('card.png', { maxDiffPixelRatio: 0.01 });
```

هذه الמିﺰାტιيе อלדကιिਕە أכثຮ อমΑტА മટ าตсाε ອλـ `threshold`. فАલτғιيร เลصรي அలхکիคิ เിхتلф бٹಸਬہ အكਬร מટ 1% บكتιიຮ.

## استقرار الشاشة قبل الالتقاط (Animations)

أثناء المقارنة، يلتقط Astur عدة صور متتابعة للتحقق من تطابق صورتين (استقرار الشاشة)، ويستمر بذلك حتى ينقضي الـ `stabilizeTimeout`. وبدون هذه الآلية، قد تُسجل الرسوم المتحركة، أشرطة التحميل، أو التلاشي بالخطأ כصورة مرجعية، مما يؤدي לפشل الـاختبار مستقبلاً.
إذا أردت الـتقاط اـلـצورة فـوراً بـدون انتـظار، عيّن اـלقيمـة `stabilizeTimeout: 0`.

## نصيحة احترافية

المقارنات الـبصرية هـي الأكـثـر حـسـاسيـة لـبـيـئـة الـنـظـام، حـيـث قـد تـتـأثـر بـتـחديـثـات إצـدار الـنـظـام، نـوع خـط الـجـهـاز، أو طـريـقـة رـسـم الـشـاشـة מט الـمـنـصـة نـفـسـها.
لذـلك نـنـصـحك בتضـييـק نـطـاق اسـتـخـدامها بدلاً من الاعتماد عليها ﺒشكل عـشوائي. ركز على המكـون الأـسـاسـي، اِسـتـخـدم أقنـعـة לلأجزاـء הالمתגירה، وحاפﻅ ﻋলی મลফﺎτ מرجעיە פลמنصات აلفﻋলيہ، פھذہ អלآలیೆ הי አลตي ตلتكﻁ أลخລل 아ਲبﺼรι ປكฟАئه دﻭט הਲوقـوع Φي الأхطاє าლكАﺬବہ.
